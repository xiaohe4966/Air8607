# 电子相册 · Air8607 实机示例

Air8607（1024×600 电容触摸屏）+ LuatOS AirUI 的全屏电子相册。照片通过 ESP32-C3 WiFi
网卡从 `img.he66.cn` 下载到 TF 卡，自动轮播，可旋转、可调亮度、可标记喜欢。

**网络是辅助，不是前提**：照片按 id 存进 TF 卡（`p_<id>.jpg` + `photos.txt` 索引），
播放的永远是本地库；ESP32-C3 只在后台补新照片，断网、网卡掉线、接口抽风都不影响
已经存下来的照片继续轮播。

```text
┌──────────────────────────────────────────────────────────┐
│ ▌喜欢照片 #29845                          ● Wi-Fi 已连接  │
│  1024 × 600 · 第 3 张 · 第 1 轮 · 2025-06-01              │
│                                                          │
│                  [        照片全屏显示        ]          │
│                                                          │
│ 本地 128 张 · 已同步 · 待下 12                  下一张 00:42 │
│ [上一张][下一张][暂停][旋转 0][喜欢][来源：喜欢][设置][刷新] │
│ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━     │
└──────────────────────────────────────────────────────────┘
```

点一下照片可隐藏顶栏/底栏和设置面板，再点一下恢复，方便纯看图。

## 功能

- **自动轮播**：默认 **5 分钟（300 秒）**一张，可在「设置 → 切换间隔」拖动滑块改为 10–300 秒；
  「暂停」冻结倒计时，「下一张」立即切换；底栏进度条显示当前这张还要停留多久。
- **黑屏已根治（需要打了补丁的固件）**：整屏解码要的 ~1.8 MB 连续内存，和 AirUI 的图片缓存
  （默认上限 3 MB，而 LVGL 堆只有约 1.5 MB）抢同一个池子，攒到第 3、4 张就分不出来 →
  `decode fail` → 照片区域黑。根因在固件，用 [`patches/patch_soc.py`](../../../patches/) 给 `.soc`
  打一个补丁（把图片缓存上限改成 1 MB，只改 1 个字节）就好，之后不再黑屏、也不用重启设备。
  没打补丁的固件上可以设 `ui_album.lua` 里的 `REBOOT_AFTER`（>0）退回「定期重启清内存」的旧办法。
- **想要彻底不黑屏**：根因在 AirUI 固件里（图片缓存按路径记 + 解码缓冲和缓存抢同一个 4 MB 池子）。
  仓库里的 [`patches/`](../../../patches/) 带了给 AirUI 加 `airui.cache_drop()` / `airui.cache_resize()`
  的补丁，打上重编一版 `.soc` 之后，相册会自动改用「单显示路径 + 换图前清缓存」，不黑屏也不用重启。
- **上一张 / 下一张**：两个按钮都只读本地相册，**不碰网络**。「下一张」按播放列表往后走，
  「上一张」沿播放历史往回走（历史最多记 64 张）。网络没连、卡没插的时候照样能用。
- **本地优先**：每张照片按 id 存成 `/sd/album/p_<id>.jpg`，索引写在 `photos.txt`
  （id、宽高、字节数、喜欢状态、拍摄时间）。播放只读本地文件，**不需要网络**。
- **网络只做增量**：C3 在后台按 25 条一页拉索引（`LIST <seq> <after_id> <limit> <filter>`），
  和本地库比对，只把没见过的 id 下载回来入库。一轮扫完（`has_more=false`）就停手，
  5 分钟后再从头扫一遍，把新照片收进来。
- **离线照常播**：C3 没连上、WiFi 断了、接口超时，底栏会显示「离线 · 只播本地」，
  正在播的照片继续播完，到点换下一张本地照片。联网后自动继续补新。
- **空间满了就停**：TF 卡不自动删旧照片（用户选择的口径）。照片写不进文件（`open_failed`）
  就判定卡满，停止下载，底栏显示「空间已满 · 已停止下载」，已存的照片照常播放；
  清理后按「刷新」恢复。没有 TF 卡时退回 `/ram`，只保留最近两张（更早的自动删掉）。
- **一轮播完自动重来**：本地库的照片洗牌成一轮，一轮播完重新洗牌；轮次存在 `state.txt`，
  重启后接着上次的轮次继续。
- **来源**：默认「喜欢照片」（`like_state=1`），可切到「全部照片」（不带 `like_state`
  过滤）。「不喜欢」和「未标记」在 C3 端有对应取值（`-1` / `0`），界面暂未开放。
  切换来源会换一份播放列表，只播该来源的照片。
- **旋转**：按 90° 循环（0°/90°/180°/270°）。180° 直接旋转；90°/270° 按屏幕比例计算缩放。
- **亮度**：PWM3 背光 10–100%，默认 100%，滑块松手立即生效；下限 10% 防止拖到全黑。
- **喜欢**：对当前照片 `REACT` 标记 `like` / `dislike` / `none`，「取消喜欢」改回 `none`，
  结果由服务端 `like_state` 回读，并同步写回 `photos.txt`。
- **固件版本检查**：C3 的 `hello` 带固件版本和协议版本。1.1.x 只有旧的 `PHOTO LIKED/RANDOM`，
  不支持分页；相册识别后停止重试并提示「C3 固件 x 不支持分页，请升级到 1.2 以上」，C3 升级
  并重新上报 `hello` 后自动恢复。
- **超时**：单张照片从发起到收完最多等 90 秒，索引页最多 60 秒。中断后按 4 秒 → 8 秒 → 15 秒
  退避重发（每次翻倍、封顶 15 秒）；确定失败的（`bad_id`、`no_token`、`no_length`、HTTP 4xx、
  超过总时限）不再重试，直接跳过，继续下一张。
- **不切坏图**：照片落盘后先校验是完整 JPEG（`FF D8` 开头、`FF D9` 结尾、≥ 4 字节），
  不合格就删文件、不入库；本地文件损坏的会被剔出库并清理索引。坏图永远不会切上去。
- **显示源直接用库里的照片文件**（`p_<id>.jpg`）：每张照片路径都不同，AirUI 的图片缓存
  （**按路径**记解码后的像素）不会命中，所以每次换图屏幕都会真的换成新照片。
  代价是缓存条目会越攒越多：整屏解码要 ~1.8 MB 连续内存，和缓存条目抢同一个池子，
  攒到 4–5 张就分不出来 → `decode fail` → 照片区域黑。
  **老固件**只能靠「每 N 张重启一次」把池子清空；**打了补丁的新固件**（见下）
  能在换图前把旧路径的缓存条目删掉，池子里永远只有一份 → 不黑屏、也不用重启。
- **解码内存是固件的限制（已用补丁解决）**：整屏 1024×600 软解要约 1.8 MB **连续** PSRAM，
  和 AirUI 的图片缓存（默认上限 3 MB）抢同一个池子，而 LVGL 堆只有约 1.5 MB → 攒到第 3、4 张
  就 `decode fail` 黑屏（PSRAM 空闲总量稳定 5.47 MB，不是泄漏，是连续块不够）。
  打了 `patches/patch_soc.py` 的补丁（图片缓存上限 1 MB）之后，实测 60 秒/张连跑 8 分钟：
  **8 次换图、0 次 decode fail**。补丁原理和用法见 [`patches/README.md`](../../../patches/README.md)。
- FAT 的修改时间只有 **2 秒精度**（秒数存的是 `>>1`）。同一条路径的两次写入要隔开 2 秒，
  否则修改时间落在同一个桶里；连着按「上一张/下一张」时相册会等一个 2 秒桶再换。
- **开机占位**：本地库还没有照片时显示内置 `/luadb/demo.jpg`，不黑屏；第一张存好就自动切过去。

## 文件

| 文件 | 作用 |
| --- | --- |
| `main.lua` | 上电时序、TF 卡挂载（结果放进 `_G.SD_READY`）、RGB 屏初始化、GT911 触摸、背光、AirUI 启动 |
| `ui_album.lua` | 1024×600 界面 + 本地照片库（读 `photos.txt`、按 id 存图、去重、轮次、倒计时）+ 后台同步状态机 |
| `photo_client.lua` | UART2 协议客户端：`LIST`/`PHOTO`/`REACT` 发送、JSON 行解析、JPEG 二进制落盘、重试/取消/保活 |
| `res/demo.jpg` | 开机演示图（1024×768，约 205 KB，烧录后位于 `/luadb/`） |
| `tp_gt911.lua` | GT911 触摸驱动（与 factory / puzzle 示例一致） |
| `exd_air8607_rgb.lua` | Air8607 RGB 屏驱动（与 factory / puzzle 示例一致） |
| `flash.sh` | 平铺当前目录（含 `res/`）并用 `luatos-cli` 烧录脚本区 |

界面（`ui_album.lua`）只通过 `photo_client` 的 `list/fetch/react/start` 接口取图和标记，
协议细节都在 `photo_client.lua` 里。

## TF 卡上的文件

| 路径 | 内容 |
| --- | --- |
| `/sd/album/p_<id>.jpg` | 一张照片一个文件，按 id 命名，播完就一直在（不会被覆写） |
| `/sd/album/photos.txt` | 本地库索引，一行一张：`id 宽 高 字节数 喜欢状态 拍摄时间` |
| `/sd/album/state.txt` | `pass=`（轮次）、`liked=`、`all=`（各来源的同步游标），每页重写一次 |

老版本留下的 `/sd/album/seen.txt` 不再使用（去重改成按 id 存库），可以直接删掉。

容量判断：`io.fsstat` 在 Air1603 的 fatfs 下不可信 —— 它报的 `total` 是 15254528、`free` 是
`4294959168`，但卡上实际已经存了 124 张、合计 17.9 MB 的照片。所以**不靠 fsstat 判断容量**，
而是靠真实写入失败：照片写不进文件（`open_failed`）就判定卡满，停下不再下载，底栏提示
「空间已满 · 已停止下载」，已存的照片照常播放。fsstat 的数字只用来打日志参考。

## 烧录

```bash
cd examples/air8607_photo_album
# 把 LuatOS-SoC_V1028_Air1603_102.soc 放到本目录，或：
#   SOC=/path/to/LuatOS-SoC_V1028_Air1603_102.soc ./flash.sh

SOC=../../firmware/LuatOS-SoC_V1028_Air1603_102.soc ./flash.sh /dev/cu.usbmodem5C490252851
./flash.sh /dev/cu.usbmodemXXXX full   # 连内核一起全量烧录
```

- 9 英寸屏把 `main.lua` 里的 `SCREEN_SIZE` 改成 `9`。
- 还需要 ESP32-C3 网卡固件：J110 `RX2/TX2` ↔ C3 GPIO4/5，见
  [`esp32c3_wifi_bridge/`](../../esp32c3_wifi_bridge/)。分页索引需要 **1.2 以上**（实测
  1.2.1）；烧录用该目录下的 `./flash_c3.sh /dev/cu.usbmodemXXXX`。
- 看日志用 `luatos-cli log view-binary --port <Air 串口> --baud 6000000 --probe --rts-reset`。
  SDK 每秒会打 `uart%d, cache %d rx msg` 的格式化噪声（无害），抓日志时按关键字过滤。

## 数据流

```text
Air8607                        ESP32-C3                        img.he66.cn
  LIST <seq> 0 25 1 ─────────▶  GET /api/photo/list?after_id=…   ─────▶
                      ◀───────  {"type":"list","ok":true,"total":229,"has_more":true,"next_after_id":29845}
                      ◀───────  {"type":"item","seq":…,"id":29845,"key":"<content_hash>","lk":1,"t":"2025-06-01 08:12:33"} ×25
                      ◀───────  {"type":"list_end","seq":…,"count":25}
  本地库没有的 id 才下载 ─▶ PHOTO <seq> 29845 ─▶  GET /api/photo/show?id=29845  ─────▶
                      ◀───────  {"type":"photo","ok":true,"id":29845,"len":74163,"w":1024,"h":600}
                      ◀───────  恰好 len 字节 JPEG（定长二进制）
  落盘 /sd/album/p_29845.jpg → 校验 SOI/EOI → 追加 photos.txt → 进播放列表
  播放：就地覆盖到 /sd/album/view_a.jpg 或 view_b.jpg（两条轮换）→ airui.image（不碰网络）
  REACT <seq> 29845 like ─────▶  POST /api/photo/react  ──────────────▶
                      ◀───────  {"type":"react","ok":true,"id":29845,"state":1}
```

- 索引回包是**纯 JSON 行**，`list` 头 + N × `item` + `list_end`；照片回包是一行 JSON 紧跟
  **定长二进制**，只有收满 `len` 字节才算下载完成，避免 JSON 和 JPEG 混在一起。
- token 只作为 C3 侧的 `X-API-Key` 请求头，不进 URL、不进日志。
- `PHOTO CANCEL` 在超时、换图或切来源时发送，C3 在 4 KB 分块之间检查并停止发送。取消后
  Air8607 先进入短暂的「静默排空」状态，丢弃在途字节再回到行模式；C3 也会用一行
  `{"type":"photo","ok":false,"err":"cancelled"}` 结束半截数据流，双方重新对齐。
- 同一时刻只有一个请求在飞（`pending` 单槽）：新的 `LIST`/`PHOTO` 会先取消旧的，避免两条
  二进制流抢占 UART；C3 也只处理最新一次请求，会丢掉旧会话残留的排队命令。
- 115200 波特率实测约 11.5 KB/s，100 KB 的照片要 10 秒左右，这是轮播等待的主要时间来源。

## 关于 token

照片接口的 token 只放在 ESP32-C3 固件的 `main/secrets.h`（已在 `.gitignore` 中），Air8607
的 Lua 脚本和本仓库都不包含 token。新环境编译 C3 前先复制模板：

```bash
cd esp32c3_wifi_bridge/main
cp secrets.h.example secrets.h
# 编辑 secrets.h，填入 PHOTO_TOKEN
```

  改用真实写入失败（`open_failed`）来判定卡满。
- 发黑的根因与修法（2026-11-01）：不是内存泄漏（PSRAM 空闲全程稳定 5.47 MB），是 **AirUI 的

  4 张左右就再也分配不出整屏软解要的 ~1.8 MB 连续内存，之后每次换图都 `decode fail`

  和网络、写卡都无关；一直显示同一张照片则 8 次全好，证实是缓存）。
  修法：**显示走两条轮换的路径**（`view_a.jpg` / `view_b.jpg`），把库里的照片**就地覆盖**上去。
  缓存是按路径记的、而且 Lua 侧没法让它作废（改文件内容/修改时间/大小、`airui.full_refresh()`、
  挪控件位置都试过，缓存照样端旧像素），所以只能用「会变的路径」让解码器重新读文件。
  另外同一时刻只能留**一张**解码结果（旧图对象先删），否则图池装不下，第 4–5 次换图就黑。
- 注意：FAT 的修改时间只有 2 秒精度，连着按「上一张/下一张」时如果两次写落在同一个桶里，
  缓存同样认不出来。现在会等到下一个桶再换（最多等 2 秒），保证屏幕上一定会更新。
- 顺带确认：AirUI 的缓存**会**因为文件变化重新读文件（把文件改成同样大小的垃圾内容，
  一样会报 `open fail: jd_prepare`），所以复用显示路径不会显示旧照片。
